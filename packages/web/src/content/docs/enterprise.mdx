OpenCode Enterprise is for organizations that want to ensure that their code and data never leaves their infrastructure. It can do this by using a centralized config that integrates with your SSO and internal AI gateway.

:::note
OpenCode does not store any of your code or context data.
:::

## Trial

OpenCode is open source and does not store any of your code or context data, so your developers can simply [get started](/docs/) and carry out a trial.

---

### Data handling

**OpenCode does not store your code or context data.** All processing happens locally or through direct API calls to your AI provider.

This means that as long as you are using a provider you trust, or an internal
AI gateway, you can use OpenCode securely.

The only caveat here is the optional `/share` feature.

---

#### Sharing conversations

If a user enables the `/share` feature, the conversation and the data associated with it are sent to the service we use to host these share pages at opencode.ai.

The data is currently served through our CDN's edge network, and is cached on the edge near your users.

We recommend you disable this for your trial.

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "share": "disabled"
}
```

[Learn more about sharing](/docs/share).

### Central Config

We can set up OpenCode to use a single central config for your entire organization.

This centralized config can integrate with your SSO provider and ensures all users access only your internal AI gateway.

---

### SSO integration

Through the central config, OpenCode can integrate with your organization's SSO provider for authentication.

This allows OpenCode to obtain credentials for your internal AI gateway through your existing identity management system.

You can also disable all other AI providers, ensuring all requests go through your organization's approved infrastructure.

## Managed Configuration

Managed configuration allows administrators to enforce organization-wide settings that users cannot override. This is critical for enterprise deployments where security policies and configuration restrictions must be consistently applied across all users.

---

### How it works

OpenCode checks for a managed configuration file in system directories during startup. If found, settings from this file take the highest priority and override all user and project configurations.

This ensures that administrative policies are enforced regardless of individual user settings.

---

### Configuration locations

The managed configuration directory varies by platform:

- **macOS**: `/Library/Application Support/opencode`
- **Windows**: `%ProgramData%\opencode` (typically `C:\ProgramData\opencode`)
- **Linux**: `/etc/opencode`

Place your `opencode.json` or `opencode.jsonc` file in the appropriate directory for your platform.

:::note
These directories require administrator privileges to write to. Users cannot modify managed configuration files.
:::

---

### Creating managed config

To create a managed configuration:

1. Create the system directory for your platform if it doesn't exist.

2. Create an `opencode.json` file in that directory with your organization's required settings.

3. Set appropriate file permissions to ensure only administrators can modify it.

Example managed configuration:

```json title="/Library/Application Support/opencode/opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "share": "disabled",
  "enabled_providers": ["your-internal-gateway"],
  "permission": {
    "bash": "ask",
    "edit": "ask"
  },
  "autoupdate": false
}
```

This configuration:
- Disables the share feature
- Restricts providers to only your internal gateway
- Requires user approval for bash and edit operations
- Disables automatic updates

---

### Priority and precedence

Managed configuration has the highest priority in OpenCode's configuration system. It loads after all other configuration sources and overrides conflicting settings.

The complete precedence order is:

1. Remote config (organizational defaults)
2. Global config (user preferences)
3. Custom config (environment variable)
4. Project config (project-specific)
5. `.opencode` directories
6. Inline config (environment variable)
7. **Managed config (highest priority)**

Settings from managed config cannot be overridden by users in their global or project configurations.

---

### Use cases

Common scenarios for managed configuration:

**Restrict AI providers**

Ensure all users connect only to approved AI providers:

```json
{
  "enabled_providers": ["your-internal-gateway"],
  "disabled_providers": ["openai", "anthropic", "gemini"]
}
```

**Enforce security policies**

Require approval for sensitive operations:

```json
{
  "permission": {
    "bash": "ask",
    "edit": "ask",
    "external_directory": "deny"
  }
}
```

**Disable features**

Turn off features not allowed in your organization:

```json
{
  "share": "disabled",
  "autoupdate": false,
  "snapshot": false
}
```

**Configure internal tools**

Set up organization-wide MCP servers or plugins:

```json
{
  "mcp": {
    "internal-tools": {
      "type": "remote",
      "url": "https://tools.company.com/mcp",
      "enabled": true
    }
  },
  "plugin": ["@company/opencode-compliance"]
}
```

---

### Testing managed config

For development and testing, you can simulate managed configuration without requiring administrator privileges using the `OPENCODE_TEST_MANAGED_CONFIG_DIR` environment variable:

```bash
export OPENCODE_TEST_MANAGED_CONFIG_DIR=/path/to/test/config
opencode run "test command"
```

This loads configuration from the specified directory with managed config priority, allowing you to verify settings before deploying to production system directories.

<details>
<summary>Can we use our own private NPM registry?</summary>

OpenCode supports private npm registries through Bun's native `.npmrc` file support. If your organization uses a private registry, such as JFrog Artifactory, Nexus, or similar, ensure developers are authenticated before running OpenCode.

To set up authentication with your private registry:

```bash
npm login --registry=https://your-company.jfrog.io/api/npm/npm-virtual/
```

This creates `~/.npmrc` with authentication details. OpenCode will automatically
pick this up.

:::caution
You must be logged into the private registry before running OpenCode.
:::

Alternatively, you can manually configure a `.npmrc` file:

```bash title="~/.npmrc"
registry=https://your-company.jfrog.io/api/npm/npm-virtual/
//your-company.jfrog.io/api/npm/npm-virtual/:_authToken=${NPM_AUTH_TOKEN}
```

Developers must be logged into the private registry before running OpenCode to ensure packages can be installed from your enterprise registry.

</details>
